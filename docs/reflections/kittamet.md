# Reflection - kittamet

## 1. Software Entropy และ Broken Window Theory

จากประสบการณ์ในการทำโปรเจกต์ที่ผ่านมา ผมเคยละเลยการตั้งชื่อไฟล์และการจัดระเบียบโค้ดให้เป็นมาตรฐาน รวมถึงปล่อยให้มีโค้ดที่ไม่ได้ใช้งานอยู่ในโปรเจกต์ เพราะคิดว่ายังไม่ส่งผลในทันที แต่เมื่อโปรเจกต์มีขนาดใหญ่ขึ้น การค้นหาและแก้ไขโค้ดทำได้ยากขึ้น สมาชิกในทีมเกิดความสับสน และใช้เวลามากขึ้นในการทำความเข้าใจโครงสร้างของโปรเจกต์ สิ่งเหล่านี้สะท้อนแนวคิดของ Software Entropy และ Broken Window Theory ที่เมื่อปล่อยให้ข้อผิดพลาดเล็ก ๆ คงอยู่ ก็จะนำไปสู่ปัญหาที่ใหญ่ขึ้นในระยะยาว

## 2. Take Responsibility

สำหรับผม หลักการ Take Responsibility คือการรับผิดชอบต่อหน้าที่ของตนเอง ยอมรับเมื่อเกิดข้อผิดพลาด และพยายามหาวิธีแก้ไขมากกว่าหาข้ออ้าง หากเกิดสถานการณ์ที่ผมไม่สามารถทำงานได้ทันตามกำหนด ผมจะไม่บอกเพียงว่า "ทำไม่ทัน" แต่จะเสนอทางเลือก เช่น ขอขยายเวลา แบ่งงานบางส่วนให้เพื่อนช่วย หรือส่งส่วนที่ทำเสร็จแล้วก่อน เพื่อให้ทีมสามารถดำเนินงานต่อได้อย่างราบรื่น หลักการ Provide Options, Don't Make Lame Excuses จะช่วยให้การสื่อสารภายในทีมมีประสิทธิภาพและลดผลกระทบต่อการทำงานร่วมกัน
