# 1. "จากแนวคิด 'Software Entropy' และ 'Broken Window Theory' ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี 'หน้าต่างที่แตก' บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?"
จากโปรเจคที่เคยทำมามีเรื่อง การตั้งชื่อไฟล์ การจัดระเบียบโค้ดและการไม่วางแผนสำหรับโครงสร้างโปรแกรมล่วงหน้ามักจะทำให้การแก้ไขและเพิ่มฟังก์ชั่นทำได้ยากและยิ่งโปรแกรมใหญ่แล้วมีการปรับปรุงส่วนที่ไม่จำเป็นออกหากไม่วางโครงสร้างไว้ล่วงหน้าอาจจะทำให้โปรแกรมล้มต่อกันเป็นทอดๆได้ เช่น ในตอนที่พัฒนาระบบที่มีหน้า Dashboard หรือมีการดึงข้อมูลจาก API ถ้าเราตั้งชื่อ Component หรือไฟล์ไม่สื่อความหมายแต่แรก และไม่มีการแยกโฟลเดอร์สำหรับ Logic กับ UI ให้ชัดเจน พอฟังก์ชันเริ่มเยอะขึ้น การจะกลับมาลบฟีเจอร์ที่ไม่ใช้ หรือปรับปรุงฐานข้อมูล จะทำได้ยากมาก เพราะโค้ดมันพันกันไปหมด จนแก้จุดนึงแล้วไปทำให้ระบบอื่นล้มเป็นทอดๆ

# 2. "อธิบายหลักการ 'Take Responsibility' ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ 'Provide Options, Don't Make Lame Excuses' ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้"
'Take Responsibility'ในความเข้าใจของผมคือการทำงานให้ตรงกับเป้าหมายที่ได้รับมาหากมีข้อผิดพลาดก็ยอมรับผิดชอบและแก้ไขหากยังแก้ได้ แล้วถ้าอยู่ในกรณีที่ใกล้ถึงกำหนดเวลาแล้วทำไม่ทันจริงๆก็จะแจ้งคนในทีมก่อนเพื่อช่วยกันหาวิธีแก้ไขปัญหาเพื่อทำงานให้อย่างน้อยที่สุดจะต้องเสร็จตามเป้าหมายที่ตั้งไว้ในตอนแรกสุด แล้วค่อยขอขยายเวลาสำหรับแก้ไขส่วนที่ผิดพลาดหากยังมีโอกาส
