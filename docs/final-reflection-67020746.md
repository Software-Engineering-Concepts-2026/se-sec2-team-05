## 1. What did you build?

งานหลักของผมในช่วงพัฒนาฟีเจอร์คือการเพิ่มวงจรการใช้งานรอบโน้ต ไม่ใช่เพียงเพิ่ม endpoint แยกส่วน:

- **การมีส่วนร่วมกับเนื้อหา:** ผู้ใช้ถามหรือเสริมข้อมูลในความคิดเห็น และให้คะแนนหลังจากเปิดดูหรือดาวน์โหลดโน้ตแล้ว
- **ข้อมูลให้เจ้าของใช้ประเมินผลงาน:** เจ้าของดูจำนวนเปิดดูและดาวน์โหลดของโน้ตแต่ละรายการ โดยแยกตัวเลขทั้งสองประเภท
- **ช่องทางดูแลเนื้อหา:** ผู้ใช้รายงานโน้ตได้ และผู้ดูแลเลือกปฏิเสธรายงานหรือเอาโน้ตออกได้

การทำงานเหล่านี้เกี่ยวข้องกับการจัดเก็บข้อมูล การตรวจสิทธิ์ การตรวจสอบ input, API response และ automated tests ตามไฟล์ที่อ้างถึงข้างต้น ไม่ได้หมายความว่าผมสร้าง NoteShare ทั้งระบบคนเดียว

ก่อนพัฒนาฟีเจอร์เหล่านี้ ผมมีส่วนร่วมใน interactive prototype สำหรับหน้า note-rating โดย commits `a7321ba`, `856e6ee` และ `35aca15` ประวัติการใช้ AI ใน [AI_USAGE.md](../AI_USAGE.md) ระบุว่ามีการใช้ GitHub Copilot และ Gemini เพื่อช่วยร่าง prototype โดยผมตรวจและปรับโครงสร้างกับ UI

## 2. What problem did you solve?

การเก็บโน้ตไว้ในระบบอย่างเดียวไม่ได้ตอบคำถามต่อจากการค้นพบไฟล์ เช่น “ควรถามใครเมื่อมีข้อสงสัย”, “โน้ตนี้มีประโยชน์กับคนอื่นหรือไม่” และ “ถ้าเนื้อหาไม่เหมาะสม ใครตรวจสอบได้” งานใน Issues #13, #14, #16 และ #18 เพิ่มกลไกที่ช่วยตอบโจทย์เหล่านี้:

- ความคิดเห็นช่วยให้ผู้ใช้ถามหรือเสริมข้อมูลใต้โน้ตได้ โดยต้องเข้าสู่ระบบเพื่อเขียน และเรียงรายการจากใหม่ไปเก่า
- Rating ให้คะแนน 1–5 หลังเข้าถึงโน้ต และผู้ใช้กลับมาเปลี่ยนคะแนนของตนเองได้
- สถิติแยก views จาก downloads และจำกัดการดูไว้ที่เจ้าของโน้ต
- Workflow รายงานแยกการปฏิเสธรายงาน ซึ่งโน้ตยังอยู่ ออกจากการเอาโน้ตที่ถูกรายงานออก

ตัวอย่างการบังคับพฤติกรรมเหล่านี้อยู่ใน [Notes Service](../services/notes-service/app.py) โดย route ที่เกี่ยวข้องตรวจสอบเงื่อนไขการเข้าถึงและสิทธิ์ของผู้ใช้ การแก้จึงเกี่ยวทั้งประโยชน์ต่อผู้ใช้และการป้องกันไม่ให้ผู้ใช้เห็นหรือแก้ข้อมูลที่ไม่ควรเข้าถึง

## 3. What technical decision are you proudest of?

การตัดสินใจทางเทคนิคที่ผมอยากยกเป็นตัวอย่างคือการให้การให้คะแนนอาศัยหลักฐานการเข้าถึงโน้ต แทนการยอมรับคะแนนจากผู้ใช้ที่ไม่เคยเปิดดูหรือดาวน์โหลดโน้ตนั้น เมื่อผู้ใช้ผ่านเงื่อนไขแล้ว ระบบเก็บ rating ของผู้ใช้ต่อโน้ตและอนุญาตให้แก้คะแนนเดิมของตนเองได้

ข้อดีของแนวทางนี้คือ rule สำคัญไม่ได้ถูกฝากไว้กับ UI อย่างเดียว แต่ backend ตรวจสอบเงื่อนไข และ tests ตรวจพฤติกรรมที่เกี่ยวข้อง ตัวอย่างชื่อ test ได้แก่ `test_authenticated_detail_open_records_eligibility`, `test_ineligible_authenticated_user_cannot_rate` และ `test_repeat_rating_updates_existing_row` ใน [rating tests](../src/tests/test_notes_ratings.py)

**ความเห็นส่วนตัว:** [สิ่งที่ผมภูมิใจคือการให้ความสำคัญกับการตรวจสอบสิทธิ์ที่ฝั่ง Backend เพราะช่วยให้ระบบตรวจสอบได้ว่าผู้ใช้มีสิทธิ์ดำเนินการนั้นจริงหรือไม่ ผมได้เรียนรู้ว่าการพัฒนาระบบไม่ได้คำนึงถึงแค่การทำให้ฟังก์ชันทำงานได้ แต่ต้องคำนึงถึงความปลอดภัยและความถูกต้องของการเข้าถึงข้อมูลด้วย]

## 4. What failure taught you the most?

บทเรียนหนึ่งที่เห็นได้จากงาน Issue #18 คือการตรวจผลข้างเคียงให้ครบ ไม่ใช่ตรวจเพียง HTTP status หรือการลบแถวในฐานข้อมูล ในประวัติการทำงานมี commit `bf4c292` ที่เพิ่ม test `test_delete_reported_note_removes_stored_file` เพื่อตรวจว่าไฟล์ใน storage ถูกลบจริงด้วย และ commit `0cdeab2` ที่ปรับปรุง test plan ให้ครอบคลุมกรณีเหล่านี้

หลักฐานนี้แสดงให้เห็นว่ามีการเติมช่องว่างด้าน test coverage ภายหลัง แต่ไม่ได้ยืนยันว่าระบบ production เคยลบไฟล์ผิดจริง ดังนั้นบทเรียนที่สรุปได้คือ เมื่อ feature มีผลต่อหลายส่วน เช่นฐานข้อมูลและไฟล์ การตรวจเพียง status code หรือ record ที่หายไปยังไม่พอ ต้องตรวจ side effects ที่ผู้ใช้และระบบส่วนอื่นพึ่งพาด้วย

**ความเห็นส่วนตัว:** [บทเรียนสำคัญที่ผมได้รับคือการทำงานร่วมกันผ่าน Branch และ Git workflow ต้องมีความเข้าใจและทำตามขั้นตอนอย่างเป็นระบบ ผมเห็นความสำคัญของการแยก Branch สำหรับงานแต่ละส่วน การ Commit การ Push และการสร้าง Pull Request เพื่อให้ทีมตรวจสอบการเปลี่ยนแปลงก่อนนำไปรวมกับ Branch หลัก ประสบการณ์นี้ทำให้ผมตระหนักว่าการจัดการโค้ดอย่างเป็นระเบียบช่วยลดความสับสนและทำงานร่วมกับทีมได้ดีขึ้น]

## 5. What would you do differently?

ถ้าทำซ้ำ ผมจะเขียน acceptance criteria และรายการ tests สำหรับผลข้างเคียงไว้ตั้งแต่เริ่มวางแผน feature ไม่รอให้มี implementation ก่อนแล้วค่อยกลับมาเติมเอกสารหรือ coverage ตัวอย่างจากงาน Issue #18 คือการเพิ่ม test ตรวจไฟล์ใน storage และการปรับ test plan ภายหลังด้วย commit `0cdeab2`

ผมจะใช้วิธีเดียวกันกับ feature อื่น โดยระบุกรณีสำเร็จ การปฏิเสธสิทธิ์ input ที่ไม่ถูกต้อง ข้อมูลไม่พบ และผลต่อข้อมูลที่เกี่ยวข้องก่อนเริ่มลงมือ จากนั้นตรวจให้ tests และเอกสารเชื่อมกับ acceptance criteria เหล่านั้น

แนวทางนี้สอดคล้องกับเป้าหมายที่ระบุไว้ใน [ข้อมูลสมาชิกทีม](../team/kittamet.md) และ [Reflection ก่อนหน้า](./reflections/kittamet.md) ซึ่งเป็นหลักฐานเกี่ยวกับเป้าหมายการเรียนรู้และประสบการณ์ก่อนหน้านี้ของผม

## 6. How did you embody Tip 52 (Delight Users)?

ผมเชื่อม Tip 52 กับการตอบโจทย์ในขั้นตอนใช้งานของแต่ละ feature:

- ผู้ใช้ที่อ่านโน้ตแล้วมีคำถามสามารถเขียนความคิดเห็น และกลับมาเห็นความคิดเห็นใหม่ก่อนรายการเก่า
- ผู้ใช้ให้คะแนนได้หลังเข้าถึงโน้ต และแก้คะแนนเดิมของตัวเองได้ แทนการให้คะแนนซ้ำ
- เจ้าของโน้ตเห็น views และ downloads แยกกัน เพื่อเข้าใจการใช้งานได้ชัดกว่าตัวเลขรวม
- ผู้ดูแลจัดการรายงานได้โดยเลือกปฏิเสธรายงานหรือเอาเนื้อหาที่ถูกรายงานออก และ tests ช่วยตรวจสอบพฤติกรรมการจัดการข้อมูลที่เกี่ยวข้อง

หลักฐานของพฤติกรรมเหล่านี้อยู่ใน [comment tests](../src/tests/test_notes_comments.py), [rating tests](../src/tests/test_notes_ratings.py), [stats tests](../src/tests/test_stats_service.py) และ [report tests](../src/tests/test_notes_reports.py)

อย่างไรก็ตาม repository ไม่มีผล user study หรือ feedback ที่ยืนยันความพึงพอใจจริง จึงไม่กล่าวอ้างว่าฟีเจอร์เหล่านี้ทำให้ผู้ใช้พึงพอใจมากขึ้นโดยไม่มีหลักฐาน

## 7. How did you embody Tip 53 (Sign Your Work)?

งานของผมสามารถตรวจสอบย้อนหลังได้ผ่าน commit history, ไฟล์ source code, tests และเอกสารที่เกี่ยวข้องกับแต่ละฟีเจอร์ ตัวอย่าง commits ที่บันทึกไว้ ได้แก่ `ce6eacf` สำหรับ rating, `da6e80a` สำหรับสถิติ และ `c3f8143` สำหรับ workflow ผู้ดูแลตรวจรายงาน

ในส่วนของผลทดสอบ ควรอ้างตัวเลขพร้อมบริบทจาก PR ต้นทางเท่านั้น ตัวเลขที่บันทึกไว้ใน Reflection เวอร์ชันก่อนหน้าระบุว่า PR #78 รายงาน Python 319 passed และ 1 xfailed, JavaScript 39 passed พร้อม `ruff check` ผ่าน ส่วน PR #77 รายงาน 308 passed และ 1 xfailed พร้อม Ruff และ `git diff --check` ผ่าน อย่างไรก็ตาม หมายเลข PR และตัวเลขเหล่านี้ควรตรวจสอบกับ PR ต้นทางก่อนนำไปใช้เป็นหลักฐานฉบับสุดท้าย และไม่ใช่ผลที่ผมรันใหม่ในการแก้ Reflection ครั้งนี้

ผมยังเปิดเผยที่มาของ prototype หน้า rating ใน [AI_USAGE.md](../AI_USAGE.md) โดยระบุบทบาทของ AI และการตรวจหรือปรับแก้ของผม การ sign งานจึงหมายถึงการทำให้เห็นว่าใครรับผิดชอบส่วนใด และให้ผู้อื่นตรวจสอบได้ ไม่ใช่การอ้างว่าไม่ได้ใช้เครื่องมือช่วย

## 8. What value did this experience add to your SE journey?

ก่อนทำงานนี้ ผมเขียนไว้ว่าอยากเข้าใจวิธีพัฒนาระบบที่มีมาตรฐานและทำงานกับทีมได้มีประสิทธิภาพ ([ข้อมูลสมาชิกทีม](../team/kittamet.md)) ประสบการณ์จาก Issues #13, #14, #16 และ #18 ทำให้เห็นจากงานจริงว่าการส่งมอบฟีเจอร์หนึ่งเกี่ยวข้องมากกว่า implementation แต่ต้องคิดถึง identity และ permission, ข้อมูลที่จัดเก็บ, ผลข้างเคียง, tests, เอกสาร และการ review ใน PR ด้วย

อีกสิ่งที่ผมเห็นจากประวัติงานคือการปรับปรุงหลัง feature ไม่ได้แปลว่าความพยายามก่อนหน้าไม่มีค่า เช่น commit ที่เติม tests และ test plan ช่วยทำให้พฤติกรรมซึ่งเดิมตรวจไม่ครบสังเกตและดูแลต่อได้ง่ายขึ้น ประสบการณ์นี้ทำให้ผมเห็นความสำคัญของการรับผิดชอบงานตั้งแต่การวางแผนจนถึงการตรวจสอบหลัง implementation

**ความเห็นส่วนตัว:** ประสบการณ์นี้ทำให้ผมเข้าใจการพัฒนาซอฟต์แวร์ในมุมของการทำงานเป็นทีมมากขึ้น ผมได้เห็นความสำคัญของการแบ่งงาน การ Review โค้ด และการเขียน Test เพื่อช่วยตรวจสอบความถูกต้องของระบบ นอกจากการเขียนโค้ดให้ทำงานได้แล้ว ผมยังได้เรียนรู้ว่าการสื่อสาร การรับข้อเสนอแนะ และการตรวจสอบงานร่วมกันเป็นส่วนสำคัญที่ช่วยให้ซอฟต์แวร์มีคุณภาพมากขึ้น
