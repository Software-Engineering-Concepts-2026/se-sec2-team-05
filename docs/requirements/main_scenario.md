# Scenarios

เอกสารนี้รวม 6 scenario ของ persona ทั้งสองตัว (ดู [personas/](./personas/)) โดย Scenario 1–3 เป็นฝั่งผู้ค้นหาโน้ต และ Scenario 4–6 เป็นฝั่งผู้แบ่งปันโน้ต ท้ายไฟล์มีรายการ edge case ที่ยังไม่ได้เขียนเป็น scenario เต็ม

## Scenario 1: การตามเนื้อหาให้ทันก่อนสอบกลางภาค

**Persona หลัก:** [เจมส์ อภิสิทธิ์ ทองมา](./personas/note_seeker.md) — นักศึกษาปี 1 คณะบริหารธุรกิจ

---

อีกสามวันจะสอบกลางภาควิชา Principles of Marketing แต่เจมส์เพิ่งนึกขึ้นได้ว่าตัวเองขาดเรียนไปสองคาบติดกันในสัปดาห์ที่แล้วเพราะตารางงานพาร์ทไทม์ชนกับตารางเรียนพอดี เขาเปิดแชทกลุ่มเพื่อนร่วมชั้นเพื่อขอโน้ตสรุปของสองคาบนั้น แต่ไม่มีใครตอบทันที เพราะแชทกลุ่มมีข้อความจากหัวข้ออื่นไหลจนโน้ตเก่าที่เคยมีคนแชร์ไว้จมหายไปในประวัติแชท เขารู้ว่าเวลาที่มีจำกัดมากในคืนนี้ จึงต้องหาทางอื่นเพื่อไม่ให้พลาดเนื้อหาสำคัญก่อนสอบ

เจมส์เปิดเว็บแอป NoteShare ที่เพื่อนเคยแนะนำไว้ ค้นหาชื่อวิชา "Principles of Marketing" แล้วกรองผลลัพธ์ตามช่วงวันที่ของคาบเรียนที่ตัวเองขาด ระบบแสดงรายการโน้ตที่ พิม เพื่อนร่วมชั้นที่ขึ้นชื่อเรื่องจดโน้ตละเอียด ได้อัปโหลดไว้ตั้งแต่หลังคาบเรียนจบ พร้อมระบุหัวข้อและวันที่ชัดเจน เจมส์เปิดดูตัวอย่างเนื้อหาก่อนดาวน์โหลด มั่นใจว่าตรงกับที่ตัวเองต้องการ จึงดาวน์โหลดไฟล์มาอ่านทบทวนและกดขอบคุณ/ให้เครดิตเจ้าของโน้ตในระบบ ภายในเวลาไม่ถึง 10 นาที เจมส์ก็ได้เนื้อหาที่ขาดหายไปครบถ้วน พร้อมสำหรับการอ่านทบทวนก่อนสอบ โดยไม่ต้องรบกวนใครในแชทกลุ่มอีกเลย

---

### โครงสร้างเรื่องเล่า (สำหรับอ้างอิงในทีม)

| องค์ประกอบ | รายละเอียด |
| --- | --- |
| **ฉากและตัวละคร** | เจมส์ นักศึกษาปี 1 ที่ต้องทำงานพาร์ทไทม์ควบคู่กับการเรียน กำลังเตรียมสอบกลางภาค |
| **เป้าหมาย** | ต้องการตามเนื้อหาวิชาที่ขาดเรียนให้ทันก่อนสอบ โดยใช้เวลาน้อยที่สุด |
| **อุปสรรค** | โน้ตจากเพื่อนกระจัดกระจายอยู่ในแชทกลุ่ม หาไม่เจอ ไม่รู้ว่าตรงกับคาบที่ขาดหรือไม่ |
| **ลำดับเหตุการณ์กับระบบ** | ค้นหาวิชา → กรองตามวันที่/หัวข้อ → ดูตัวอย่างเนื้อหา → ดาวน์โหลด → ให้เครดิตเจ้าของโน้ต |
| **ผลลัพธ์** | ได้เนื้อหาที่ขาดหายไปครบถ้วนภายในเวลาสั้นๆ โดยไม่ต้องพึ่งพาเพื่อนโดยตรง |

## Scenario 2: กรองหาโน้ตแล็บที่พลาดให้ตรงจุดที่สุด

**Persona หลัก:** [เจมส์ อภิสิทธิ์ ทองมา](./personas/note_seeker.md) — นักศึกษาปี 1 คณะบริหารธุรกิจ

---

สัปดาห์นี้เจมส์ขาดแล็บวิชา Business Computing ไปหนึ่งครั้งเพราะกะงานพาร์ทไทม์ถูกเลื่อนกะทันหัน เขามีเวลาว่างแค่ 20 นาทีก่อนต้องรีบไปทำงานต่อ จึงเปิด NoteShare แล้วเลือกตัวกรองคณะ (บริหารธุรกิจ) ชั้นปี (ปี 1) และประเภทไฟล์ (เอกสารสรุป ไม่เอาสไลด์ภาพนิ่งอย่างเดียว) เพื่อตัดผลลัพธ์ที่ไม่เกี่ยวข้องออกไปก่อน จากนั้นกรองต่อด้วยช่วงวันที่ของแล็บที่ขาดและคำค้นหัวข้อเฉพาะ ระบบเหลือผลลัพธ์เพียงไม่กี่รายการ เจมส์เปิดดูตัวอย่างเนื้อหาของโน้ตอันดับแรกก่อนตัดสินใจ เพื่อไม่ให้เสียเวลาดาวน์โหลดไฟล์ที่ไม่ตรงกับที่ต้องการ เมื่อเห็นว่าเนื้อหาตรงกับหัวข้อแล็บที่พลาดจริง เขาจึงดาวน์โหลดและให้คะแนนโน้ตนั้นหลังจากอ่านจบ เพื่อเป็นข้อมูลให้คนอื่นที่มาค้นหาทีหลังตัดสินใจง่ายขึ้น ส่วนโน้ตอีกสองรายการที่เหลือในผลการค้นหาซึ่งดูน่าจะมีประโยชน์แต่ยังไม่มีเวลาอ่านตอนนี้ เจมส์กดเก็บไว้ใน "รายการโปรด" ก่อน เพื่อกลับมาเปิดอ่านต่อหลังเลิกกะทำงาน โดยไม่ต้องมาไล่ตั้งตัวกรองชุดเดิมใหม่ทั้งหมดอีกรอบ

---

### โครงสร้างเรื่องเล่า (สำหรับอ้างอิงในทีม)

| องค์ประกอบ | รายละเอียด |
| --- | --- |
| **ฉากและตัวละคร** | เจมส์ มีเวลาว่างจำกัดมากก่อนกะทำงาน ต้องหาโน้ตแล็บที่ขาดให้เจอเร็วที่สุด |
| **เป้าหมาย** | หาโน้ตของแล็บที่พลาดให้ตรงกับหัวข้อและวันที่จริง โดยไม่เสียเวลาไปกับผลลัพธ์ที่ไม่เกี่ยวข้อง |
| **อุปสรรค** | ผลการค้นหาด้วยชื่อวิชาอย่างเดียวมีจำนวนมากเกินไป ปนกันทั้งวิชาปีอื่นและประเภทไฟล์ที่ไม่ตรงความต้องการ |
| **ลำดับเหตุการณ์กับระบบ** | กรองตามคณะ/ชั้นปี/ประเภทไฟล์ → กรองตามวันที่/หัวข้อ → ดูตัวอย่างเนื้อหา → ดาวน์โหลด → ให้คะแนนโน้ต → บันทึกโน้ตที่เหลือไว้ในรายการโปรด |
| **ผลลัพธ์** | ได้โน้ตที่ตรงกับแล็บที่ขาดภายในเวลาไม่กี่นาที ช่วยให้คนอื่นเลือกโน้ตได้ง่ายขึ้นจากคะแนนที่ให้ไว้ และเก็บโน้ตที่ยังไม่ได้อ่านไว้กลับมาต่อได้โดยไม่ต้องค้นซ้ำ |

---

## Scenario 3: รายงานโน้ตที่ติดป้ายผิดวิชา

**Persona หลัก:** [เจมส์ อภิสิทธิ์ ทองมา](./personas/note_seeker.md) — นักศึกษาปี 1 คณะบริหารธุรกิจ

---

เจมส์ค้นหาโน้ตวิชา Financial Accounting เพื่อทบทวนก่อนสอบ และดาวน์โหลดไฟล์ที่ระบบขึ้นว่าตรงกับหัวข้อที่ต้องการ แต่พอเปิดอ่านจริงกลับพบว่าเนื้อหาข้างในเป็นสรุปของวิชาคนละตัวที่บังเอิญใช้คำที่คล้ายกัน คาดว่าเจ้าของโน้ตติดป้ายวิชาผิดตอนอัปโหลด เจมส์รู้สึกเสียเวลาที่ดาวน์โหลดมาแล้วใช้ไม่ได้ จึงกดรายงานโน้ตนั้นพร้อมระบุเหตุผลว่าเนื้อหาไม่ตรงกับวิชาที่ระบุไว้ แทนที่จะปล่อยผ่านเฉยๆ เพราะรู้ว่าถ้าไม่แจ้ง คนอื่นที่ค้นหาด้วยชื่อวิชาเดียวกันก็จะเจอปัญหาแบบเดียวกันอีก

ก่อนปิดหน้านั้นไป เจมส์เขียนความคิดเห็นไว้ใต้โน้ตด้วยว่าเนื้อหาข้างในดูเป็นวิชาอะไร และถามเจ้าของโน้ตตรง ๆ ว่าติดป้ายวิชาสลับกันหรือเปล่า เพราะการรายงานเป็นเรื่องระหว่างเขากับผู้ดูแลระบบซึ่งกินเวลาตรวจสอบ ส่วนคอมเมนต์เป็นสิ่งที่คนอื่นที่เข้ามาเจอโน้ตนี้ก่อนผู้ดูแลจะจัดการเสร็จมองเห็นได้ทันที และเปิดทางให้เจ้าของโน้ตแก้ป้ายเองได้เลยถ้าเป็นแค่ความพลั้งเผลอ

---

### โครงสร้างเรื่องเล่า (สำหรับอ้างอิงในทีม)

| องค์ประกอบ | รายละเอียด |
| --- | --- |
| **ฉากและตัวละคร** | เจมส์ กำลังทบทวนก่อนสอบวิชา Financial Accounting และเจอโน้ตที่เนื้อหาไม่ตรงกับป้ายกำกับวิชา |
| **เป้าหมาย** | ได้เนื้อหาที่ตรงกับวิชาที่ต้องการทบทวน และรักษาคุณภาพผลการค้นหาให้คนอื่นในระบบด้วย |
| **อุปสรรค** | โน้ตถูกติดป้าย/หมวดหมู่วิชาผิดตั้งแต่ตอนอัปโหลด ทำให้ผลการค้นหาไม่น่าเชื่อถือ |
| **ลำดับเหตุการณ์กับระบบ** | ค้นหาวิชา → ดาวน์โหลดโน้ต → พบว่าเนื้อหาไม่ตรง → กดรายงานโน้ตพร้อมระบุเหตุผล → เขียนคอมเมนต์ใต้โน้ตแจ้งคนอื่นและถามเจ้าของโน้ต |
| **ผลลัพธ์** | ระบบมีข้อมูลไว้ตรวจสอบและแก้ไขป้ายกำกับ ลดโอกาสที่คนอื่นจะเจอปัญหาเดียวกันซ้ำ และคนที่เข้ามาเจอโน้ตนี้ระหว่างรอผู้ดูแลตรวจสอบก็เห็นคำเตือนจากคอมเมนต์ก่อนเสียเวลาดาวน์โหลด |

## Scenario 4: อัปโหลดโน้ตพร้อมข้อมูลครบ ตัดปัญหาถูกทักซ้ำ

**Persona หลัก:** [พิมพ์ชนก "พิม" วงศ์สุวรรณ](./personas/note_contributor.md) — นักศึกษาปี 3 คณะวิศวกรรมคอมพิวเตอร์

---

หลังจบคาบ Data Structures พิมเปิด NoteShare ทันทีตามความเคยชิน อัปโหลดไฟล์สรุปที่เพิ่งจดจบ พร้อมกรอกข้อมูลวิชา หัวข้อของคาบนั้น และวันที่เรียนให้ครบถ้วน เพราะรู้ดีว่าถ้าใส่ข้อมูลไม่ชัดเจน จะมีเพื่อนทักมาถามซ้ำในไลน์ว่านี่ใช่โน้ตของคาบที่ตัวเองพลาดหรือเปล่า เมื่อกรอกเมทาดาต้าครบ ระบบจะให้เครดิตชื่อพิมติดกับไฟล์โดยอัตโนมัติทุกครั้งที่มีคนดาวน์โหลด สัปดาห์นี้พอมีเพื่อนถามหาโน้ตคาบนี้ในแชทกลุ่มอีก พิมแค่ส่งลิงก์ไฟล์ในระบบให้แทนที่จะต้องเปิดหาไฟล์แล้วส่งเองทีละคนเหมือนเดิม

---

### โครงสร้างเรื่องเล่า (สำหรับอ้างอิงในทีม)

| องค์ประกอบ | รายละเอียด |
| --- | --- |
| **ฉากและตัวละคร** | พิม เพิ่งจดโน้ตคาบ Data Structures จบ กำลังจะอัปโหลดตามความเคยชิน |
| **เป้าหมาย** | แชร์โน้ตให้เพื่อนหาเจอเองได้ โดยไม่ต้องตอบคำถามหรือส่งไฟล์ซ้ำให้ทีละคน |
| **อุปสรรค** | ถ้าใส่ข้อมูลวิชา/หัวข้อ/วันที่ไม่ครบ เพื่อนจะทักถามซ้ำเพื่อยืนยันว่าเป็นไฟล์ที่ต้องการจริงหรือไม่ |
| **ลำดับเหตุการณ์กับระบบ** | อัปโหลดไฟล์ → กรอกเมทาดาต้า (วิชา/หัวข้อ/วันที่) → ระบบผูกเครดิตชื่อพิมอัตโนมัติ → ส่งลิงก์แทนไฟล์เมื่อมีคนถามซ้ำ |
| **ผลลัพธ์** | ลดจำนวนครั้งที่ต้องตอบแชทซ้ำเรื่องไฟล์เดิม และเครดิตติดกับผลงานของตัวเองอัตโนมัติ |

## Scenario 5: เห็นคำขอบคุณจากคนที่ไม่เคยรู้จัก

**Persona หลัก:** [พิมพ์ชนก "พิม" วงศ์สุวรรณ](./personas/note_contributor.md) — นักศึกษาปี 3 คณะวิศวกรรมคอมพิวเตอร์

---

ระหว่างพักเบรกวันเสาร์ พิมเปิดหน้าสถิติผู้อัปโหลดในบัญชีของตัวเองตามที่ทำเป็นประจำทุกสัปดาห์ เพื่อดูว่าโน้ตที่แชร์ไปถูกดาวน์โหลดไปกี่ครั้งแล้ว หน้าสถิติแสดงว่ามีนักศึกษาอีกคนหนึ่งที่พิมไม่เคยรู้จักมาก่อนกดขอบคุณ/ให้เครดิตโน้ตวิชา Operating Systems ที่เธออัปโหลดไว้เมื่อสองสัปดาห์ก่อน พิมรู้สึกดีที่เห็นว่าสิ่งที่ตัวเองสรุปไว้เพื่อทบทวนเองมีประโยชน์กับคนที่ไม่รู้จักกันด้วย ไม่ใช่แค่เพื่อนในกลุ่มแชทเหมือนเมื่อก่อน ทำให้อยากอัปโหลดโน้ตของคาบต่อๆ ไปอย่างสม่ำเสมอต่อไป

---

### โครงสร้างเรื่องเล่า (สำหรับอ้างอิงในทีม)

| **เป้าหมาย** | อยากรู้ว่าโน้ตที่แชร์ไปมีคนนำไปใช้จริงหรือเป็นประโยชน์แค่ไหน |
| **อุปสรรค** | ก่อนหน้านี้ไม่มีทางรู้เลยว่าโน้ตที่แชร์ผ่านแชทกลุ่มถูกใช้ต่อหรือเป็นประโยชน์กับใครบ้าง |
| **ลำดับเหตุการณ์กับระบบ** | เปิดหน้าสถิติ/เครดิตของตัวเอง → เห็นรายการขอบคุณจากผู้ดาวน์โหลด → รับรู้ว่ามีคนแปลกหน้าได้ประโยชน์จากโน้ตของตน |
| **ผลลัพธ์** | ได้รับการยืนยันคุณค่าของโน้ตที่ทำ เสริมแรงจูงใจให้อัปโหลดต่อเนื่อง |

## Scenario 6: แก้ไขโน้ตเก่าแทนการอัปโหลดใหม่

**Persona หลัก:** [พิมพ์ชนก "พิม" วงศ์สุวรรณ](./personas/note_contributor.md) — นักศึกษาปี 3 คณะวิศวกรรมคอมพิวเตอร์

---

พิมย้อนกลับไปเปิดโน้ตวิชา Database Systems ที่อัปโหลดไว้เมื่อสัปดาห์ก่อนเพื่อใช้ทบทวนอีกรอบ และสังเกตเห็นว่าตัวเองพิมพ์สูตรคำนวณผิดไปจุดหนึ่งตอนจดสรุป เธอไม่อยากปล่อยให้ข้อมูลผิดค้างอยู่ในระบบ เพราะรู้ว่ามีคนดาวน์โหลดไฟล์นี้ไปแล้วหลายคน แทนที่จะอัปโหลดไฟล์ใหม่ซ้อนขึ้นมาอีกไฟล์ พิมเข้าไปที่โน้ตเดิมของตัวเองแล้วแก้ไขเนื้อหาโดยตรง ทำให้คนที่เคยดาวน์โหลดไปแล้วหรือจะเข้ามาเจอทีหลังได้เห็นเวอร์ชันที่ถูกต้อง โดยไม่ต้องมีไฟล์เก่าผิดๆ ค้างปนอยู่ในระบบให้สับสน

---

### โครงสร้างเรื่องเล่า (สำหรับอ้างอิงในทีม)

| องค์ประกอบ | รายละเอียด |
| --- | --- |
| **ฉากและตัวละคร** | พิม พบว่าโน้ตวิชา Database Systems ที่อัปโหลดไว้ก่อนหน้ามีจุดผิดพลาด |
| **เป้าหมาย** | แก้ไขข้อมูลที่ผิดให้ถูกต้อง โดยไม่สร้างความสับสนจากไฟล์ซ้ำซ้อนในระบบ |
| **อุปสรรค** | ถ้าไม่มีทางแก้ไขไฟล์เดิม จะต้องอัปโหลดใหม่ทับ ทำให้มีทั้งไฟล์ถูกและผิดปนกันอยู่ |
| **ลำดับเหตุการณ์กับระบบ** | เปิดโน้ตของตัวเอง → พบจุดผิด → แก้ไขเนื้อหาโน้ตเดิมโดยตรง → บันทึกการเปลี่ยนแปลง |
| **ผลลัพธ์** | โน้ตในระบบมีเวอร์ชันที่ถูกต้องเพียงชุดเดียว ไม่มีไฟล์ผิดพลาดตกค้างให้คนอื่นสับสน |

## Edge Cases

- **ค้นหาไม่พบผลลัพธ์เลย** — เช่น เจมส์ค้นหาวิชา/หัวข้อที่ยังไม่มีใครอัปโหลดโน้ตไว้ ระบบต้องแจ้งให้ชัดเจนว่าไม่พบผลลัพธ์ แทนที่จะแสดงหน้าว่างเฉยๆ
- **อัปโหลดไม่สำเร็จ/ไฟล์ใหญ่เกินกำหนด** — พิมพยายามอัปโหลดไฟล์สแกนโน้ตความละเอียดสูงแล้วระบบปฏิเสธเพราะเกินขนาดที่กำหนด ต้องมีข้อความแจ้งเหตุผลและแนวทางแก้ (เช่น บีบอัดไฟล์)
- **รายงานที่ตรวจสอบแล้วไม่เป็นปัญหาจริง** — มีคนรายงานโน้ตของพิมว่าไม่ตรงวิชา แต่แอดมินตรวจสอบแล้วพบว่าเนื้อหาถูกต้อง ระบบต้องรองรับการยกเลิก/ปิดเคสรายงานนั้นได้โดยไม่กระทบสถานะโน้ต
- **โน้ตซ้ำซ้อนจากคนละคน** — นักศึกษาสองคนอัปโหลดสรุปของเลกเชอร์เดียวกันในเวลาไล่เลี่ยกัน ทำให้ผลการค้นหามีโน้ตเนื้อหาใกล้เคียงกันหลายไฟล์ ผู้ค้นหาต้องมีข้อมูลพอจะเทียบเลือกได้ (เช่น คะแนน/วันที่อัปโหลด)
- **เจ้าของโน้ตลบบัญชีตัวเอง** — ต้องมีนโยบายชัดเจนว่าโน้ตที่เคยอัปโหลดไว้และเครดิตที่เคยได้รับจะเกิดอะไรขึ้น เช่น ยังคงอยู่ในระบบแบบไม่ระบุตัวตน หรือถูกลบไปพร้อมบัญชี
