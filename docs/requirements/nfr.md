# Non-Functional Requirements (NFR)

เอกสารนี้ขยายหัวข้อ "Non-Functional Requirements" ใน [srs.md](./srs.md) ให้เป็นข้อกำหนดที่ตรวจสอบได้ (testable) โดยอิงจากสถาปัตยกรรมจริงที่ระบุใน [architecture/README.md](../architecture/README.md) และ [ADR-001](../architecture/adr/0001-tech-stack-selection.md): SPA (React + Vite) เรียก Flask microservices ผ่าน API Gateway ที่ตรวจ JWT, ข้อมูลอยู่ใน PostgreSQL, ไฟล์โน้ตอยู่ใน S3-compatible object storage, แพ็กเป็น Docker แล้ว deploy backend บน Render/Railway (free tier) และ frontend บน Vercel

แต่ละข้อมีรหัส NFR-XXX เพื่ออ้างอิงในแผนทดสอบ (test plan) ต่อไป

## 1. Performance

| ID | ข้อกำหนด |
| --- | --- |
| NFR-001 | หน้าจอหลัก (หน้า Search และหน้า Note detail) ต้องแสดงผล (First Contentful Paint) ภายใน 2 วินาที บนอินเทอร์เน็ตทั่วไป (4G/บ้าน) เมื่อ service ที่เกี่ยวข้อง "อุ่นเครื่อง" แล้ว (ไม่นับ cold start ครั้งแรก — ดูข้อ 4) |
| NFR-002 | คำค้นหาโน้ต (ค้นชื่อวิชา/หัวข้อ ผ่าน Notes Service) ต้องคืนผลลัพธ์ภายใน 3 วินาที นับจากกดค้นหาถึงเห็นรายการบนหน้าจอ |
| NFR-003 | การอัปโหลดไฟล์โน้ตขนาดไม่เกิน 10 MB ต้องแสดงสถานะความคืบหน้า (progress) ให้ผู้ใช้เห็นภายใน 1 วินาทีหลังกดอัปโหลด เพื่อไม่ให้ผู้ใช้คิดว่าระบบค้าง

## 2. Security

| ID | ข้อกำหนด |
| --- | --- |
| NFR-004 | รหัสผ่านผู้ใช้ต้องถูก hash (เช่น bcrypt) ก่อนบันทึกลง PostgreSQL เสมอ — ห้ามเก็บ plaintext ในฐานข้อมูลหรือ log ใดๆ |
| NFR-005 | ทุก request จาก SPA ไปยัง API Gateway ที่เข้าถึงข้อมูลส่วนตัว (upload, edit, delete, profile) ต้องแนบ JWT ที่ยังไม่หมดอายุ; API Gateway ปฏิเสธ request ที่ไม่มี token หรือ token invalid ด้วย HTTP 401 ก่อนส่งต่อไปยัง service ปลายทาง |
| NFR-006 | Notes Service ต้องตรวจสอบไฟล์อัปโหลดทั้งชนิดไฟล์ (จำกัดเฉพาะ PDF และรูปภาพที่กำหนด เช่น JPG/PNG) และขนาดไฟล์ (ไม่เกิน 10 MB ต่อไฟล์) ก่อนบันทึกลง object storage และปฏิเสธไฟล์ที่ไม่ผ่านเงื่อนไขทันที |
| NFR-007 | การแก้ไขหรือลบโน้ตทำได้เฉพาะเจ้าของโน้ตเท่านั้น — Notes Service ต้องเทียบ user id จาก JWT กับเจ้าของ record ทุกครั้งก่อนอนุญาต ผู้ใช้อื่นที่พยายามแก้ไข/ลบโน้ตที่ไม่ใช่ของตัวเองต้องได้รับ HTTP 403

## 3. Usability

| ID | ข้อกำหนด |
| --- | --- |
| NFR-008 | UI ต้องเป็น mobile-first และใช้งานได้ครบทุกฟังก์ชันหลัก (ค้นหา, ดูตัวอย่าง, ดาวน์โหลด, อัปโหลด) แบบมือเดียวบนหน้าจอมือถือขนาดทั่วไป (~375–414px width) สอดคล้องกับพฤติกรรมของ James ที่ใช้มือถือเป็นอุปกรณ์หลัก |
| NFR-009 | ผู้ใช้ใหม่ที่ไม่ถนัดเทคโนโลยี (เช่น นักศึกษาปี 1) ต้องสามารถค้นหาและดาวน์โหลดโน้ตได้สำเร็จโดยไม่ต้องมี onboarding หรือคู่มือ — ปุ่มค้นหาและตัวกรองหลักต้องมองเห็นได้ทันทีในหน้าแรกโดยไม่ต้อง scroll

## 4. Availability / Reliability

| ID | ข้อกำหนด |
| --- | --- |
| NFR-010 | ยอมรับได้ที่ backend บน free-tier host (Render/Railway) จะมี cold-start delay (service "หลับ" แล้วต้องปลุก) เมื่อไม่มีการใช้งานช่วงหนึ่ง แต่ระบบต้องฟื้นตัวเอง (auto-restart/auto-wake) เมื่อมี request เข้ามาโดยไม่ต้องมีคนแอดมินเข้าไป restart ด้วยมือ |
| NFR-011 | เมื่อ service ใด service หนึ่ง (เช่น Stats Service) ล่มหรือตอบช้า SPA ต้องยังใช้งานฟังก์ชันหลัก (ค้นหา/ดาวน์โหลด/อัปโหลด) ต่อได้ โดยแสดงข้อความแจ้งเตือนเฉพาะส่วนที่เกี่ยวข้อง (เช่น สถิติยอดดาวน์โหลดโหลดไม่สำเร็จ) แทนที่จะทำให้ทั้งหน้าใช้งานไม่ได้

## 5. Compatibility

| ID | ข้อกำหนด |
| --- | --- |
| NFR-012 | SPA ต้องทำงานได้ถูกต้องบน Chrome, Edge, และ Safari เวอร์ชันล่าสุด (current stable) ทั้งบน desktop และ mobile โดยไม่ต้องติดตั้งแอปเนทีฟ (native app) ใดๆ

## 6. Maintainability

| ID | ข้อกำหนด |
| --- | --- |
| NFR-013 | แต่ละ microservice (API Gateway, User & Auth, Notes, Stats) ต้องมี Dockerfile ของตัวเอง สามารถ build และ deploy แยกจากกันได้โดยไม่ต้อง rebuild service อื่น สอดคล้องกับการแบ่ง service ใน ADR-001

## 7. Scalability

| ID | ข้อกำหนด |
| --- | --- |
| NFR-014 | โปรเจกต์นี้เป็นงานระดับนักศึกษา (3 คน, 1 เทอม) — **ไม่ตั้ง NFR สำหรับรองรับผู้ใช้พร้อมกันจำนวนมากหรือโหลดระดับ production** การรองรับ concurrent load สูงถือเป็นข้อจำกัดที่ยอมรับ (accepted limitation) ของ scope นี้ ไม่ใช่สิ่งที่ต้องส่งมอบ
