# ADR-004: ใช้ edit token ต่อโน้ตเป็นตัวแทนการตรวจสอบเจ้าของชั่วคราว

[🌐 English](./0004-per-note-edit-token.md) · **ภาษาไทย**

**สถานะ:** ถูกแทนด้วย [ADR-013](./0013-retire-per-note-edit-token.th.md) — เลิกใช้ token แล้ว การแก้/ลบต้อง login เป็นเจ้าของ · ก่อนหน้านั้นแก้ไขเพิ่มเติมโดย [ADR-008](./0008-owner-login-for-note-changes.th.md): เจ้าของที่ login อยู่แก้/ลบได้โดยไม่ต้องมี token และ token ยังใช้ได้

**บริบท:**
US-19 (#19) และ US-20 (#20) มี acceptance criteria ข้อเดียวกันว่า "เจ้าของเท่านั้น" ที่แก้หรือลบโน้ตได้ แต่ระบบยังไม่มี identity ที่เชื่อถือได้เลย — [ADR-003](./0003-tracer-bullet-scope.th.md) ตั้งใจเลื่อน User & Auth Service (#5, #6) ออกไป และ `uploader_name` ก็มาจากฟอร์มอัปโหลดแล้วแสดงอยู่บนโน้ตทุกใบ ถ้าเอาค่านี้ที่ส่งมากับ request ไปเทียบกับที่เก็บไว้ เท่ากับไม่ได้ตรวจอะไรเลย เพราะเป็นค่าสาธารณะที่ใครก็พิมพ์ตามได้

ทางเลือกจึงมีสามทาง: ส่งงานทั้งที่การตรวจสิทธิ์ใช้ไม่ได้จริง, หยุดทั้งสอง story ไว้รอ authentication, หรือหากลไกชั่วคราวที่บังคับ criteria ข้อนี้ได้จริง ทางแรกคือการทำผิดซ้ำรอยที่ ADR-003 วิจารณ์ตัวเองไว้ — ปิด story ด้วยงานที่ไม่ผ่าน acceptance criteria ของมันเอง ส่วนทางที่สองทำให้ story ระดับ Must ของ Sprint 1 สองเรื่องค้างอยู่หลัง service ที่ทีมยังไม่ได้เริ่มทำ

**การตัดสินใจ:**
ให้ `notes-service` ออก **edit token ประจำโน้ตแต่ละใบ**:

*   `POST /notes` สุ่มค่า 256 บิต (`secrets.token_urlsafe(32)`) แล้วคืนให้ **ครั้งเดียว** ใน response ตอนสร้างเท่านั้น
*   เก็บเฉพาะ SHA-256 hash ของ token ไว้ที่คอลัมน์ `notes.edit_token_hash` ตัว token จริงไม่ถูกเขียนลงฐานข้อมูล ไม่ลง log และไม่ถูกคืนจาก endpoint อื่นใดอีก
*   `PATCH /notes/<id>` และ `DELETE /notes/<id>` ต้องแนบ token มาใน header `X-Note-Token` แล้วเทียบด้วย `secrets.compare_digest` ถ้าไม่ส่งมาหรือส่งผิดจะได้ `403`
*   ใช้ SHA-256 เปล่า ๆ ไม่ต้อง key stretching เพราะ token เป็นค่าสุ่ม entropy สูงที่เครื่องสร้างเอง ไม่ใช่รหัสผ่านที่คนตั้ง จึงไม่มีอะไรให้ brute-force หรือเทียบ rainbow table
*   endpoint ที่อ่านอย่างเดียวยังเปิดตามเดิมเหมือนที่ ADR-003 กำหนดไว้

กลไกทั้งหมดอยู่ในไฟล์เดียวคือ `services/notes-service/tokens.py` เพื่อให้การถอดออกทีหลังเป็นการแก้ที่จำกัดวง

**นี่ไม่ใช่ authentication** ไม่มี identity ไม่มี session ไม่มีการ login ไม่มีการเพิกถอน token และถ้าผู้ใช้ทำ token หายก็กู้คืนไม่ได้ มันเป็นแค่การตรวจสิทธิ์ต่อโน้ตใบเดียวเท่านั้น

**ผลที่ตามมา:**
*   **ข้อดี:**
    *   criteria ข้อ "เจ้าของเท่านั้น" ของ #19 และ #20 ถูกบังคับจริงในแบบที่ทดสอบได้ ไม่ใช่แค่เคลม — มีเทสต์ยืนยันว่า token ของโน้ตใบหนึ่งใช้กับใบอื่นไม่ได้
    *   ทั้งสอง story เดินหน้าได้โดยไม่ต้องรอ User & Auth Service
    *   เส้นทางย้ายไปของจริงสั้นมาก เมื่อ #5/#6 เสร็จให้ลบ `tokens.py` กับคอลัมน์ `edit_token_hash` แล้วเปลี่ยนไปตรวจ `note.owner_id == current_user.id` แทน
*   **ข้อเสีย:**
    *   ถ้าทำ token หาย เจ้าของจะแก้หรือลบโน้ตของตัวเองไม่ได้อีก และยังไม่มีช่องทางของ admin ให้กู้ ยอมรับได้เพราะยังไม่มีอะไร deploy และยังไม่มีข้อมูลจริง
    *   token ส่งไปเป็น header เปล่า ๆ จึงปลอดภัยเท่าที่ transport ปลอดภัย — `notes-service` ต้องไม่อยู่บนอินเทอร์เน็ตสาธารณะจนกว่า #5/#6 จะเสร็จ ซึ่ง ADR-003 กำหนดไว้อยู่แล้ว
    *   client ที่จะให้ผู้ใช้แก้โน้ตได้ต้องเก็บ token เอง เป็นภาระที่ flow auth ของจริงจะมาช่วยตัดทิ้ง
    *   การเพิ่ม `edit_token_hash` กับ `updated_at` เป็นการเปลี่ยน schema และยังไม่มี migration tool (ADR-003) จึงต้อง `docker compose down -v` ในเครื่อง dev
