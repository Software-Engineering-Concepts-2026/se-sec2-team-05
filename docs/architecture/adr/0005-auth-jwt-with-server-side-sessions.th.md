# ADR-005: User & Auth Service ที่ออก JWT โดยมี session ฝั่งเซิร์ฟเวอร์รองรับ

[🌐 English](./0005-auth-jwt-with-server-side-sessions.md) · **ภาษาไทย**

**สถานะ:** Accepted

**บริบท:**
[ADR-003](./0003-tracer-bullet-scope.th.md) เลื่อน User & Auth Service ออกไป ทำให้ทุก endpoint ของ Notes Service ไม่มีการยืนยันตัวตน และ `uploader_name` ปลอมได้ง่าย ๆ US-05 (#5) กับ US-06 (#6) เป็น story ระดับ Must ของ Sprint 1 ที่มาปิดช่องนี้

*   #5 — สมัครได้เฉพาะอีเมลโดเมนมหาวิทยาลัย, ไม่ยอมให้อีเมลซ้ำ, รหัสผ่านต้อง hash ก่อนบันทึก, และ error ต้องอ่านเข้าใจง่าย
*   #6 — login ด้วยอีเมล+รหัสผ่าน, **logout แล้วต้อง invalidate session/token ทันที**, login ไม่ผ่านต้องไม่บอกว่าผิดช่องไหน (กัน enumeration), และคงสถานะ login ไว้จนกว่าจะ logout หรือ token หมดอายุ

NFR เพิ่มข้อกำหนดอีกสามข้อ: NFR-004 (hash รหัสผ่าน "เช่น bcrypt" ห้ามเก็บ plaintext), NFR-005 (request ที่เข้าถึงข้อมูลส่วนตัวต้องแนบ JWT ที่ยังไม่หมดอายุ และ API Gateway ต้องปฏิเสธด้วย 401) และ NFR-013 (ทุก microservice มี Dockerfile ของตัวเอง) ส่วน [C4 Container diagram](../c4-container.md) กำหนดให้ User & Auth Service ดูแล "registration, login (hashed passwords), JWT issuance"

ข้อกำหนดเหล่านี้ขัดกันเองอยู่ JWT ธรรมดาตรวจได้ในตัวเอง จึงเพิกถอนก่อนหมดอายุไม่ได้ ถ้าใช้ JWT อย่างเดียวจะทำข้อ "logout แล้ว invalidate ทันที" ไม่ได้ และ NFR-005 ก็สมมติว่ามี API Gateway ซึ่งตาม ADR-003 ยังไม่มี

**การตัดสินใจ:**
สร้าง container `auth-service` แยกออกมา (Flask + SQLAlchemy, พอร์ต 5002, มี Dockerfile ของตัวเอง) ใช้ฐานข้อมูล PostgreSQL ก้อนเดิมร่วมกับ service อื่น แต่มีตารางของตัวเองคือ `users` และ `auth_sessions`

*   **สมัครสมาชิก** (`POST /auth/register`) — ตัดช่องว่างหัวท้ายของอีเมลและแปลงเป็นตัวพิมพ์เล็ก โดเมนต้อง**ตรงตัว**กับค่าใดค่าหนึ่งใน `ALLOWED_EMAIL_DOMAINS` (คั่นด้วย comma ค่าเริ่มต้นคือ `up.ac.th` และไม่นับ subdomain) รหัสผ่านยาว 8–128 ตัวอักษรและไม่ตัดช่องว่าง `display_name` ผู้ใช้ตั้งเอง ยาว 1–120 ตัวอักษร ช่องที่ผิดจะถูกรายงานครบในครั้งเดียว (`400`) ส่วนอีเมลซ้ำได้ `409` ซึ่งรวมถึงกรณีสมัครพร้อมกันที่ไปชน unique constraint ด้วย
*   **Access token** (`POST /auth/login`) — เป็น JWT แบบ HS256 อายุ **8 ชั่วโมง** และ**ไม่มี refresh token** มี claim `sub` (user id), `jti`, `iat`, `exp`, `iss` การ login แต่ละครั้งจะสร้างแถวใน `auth_sessions` หนึ่งแถว โดยใช้ `jti` เป็น key
*   **การตรวจ token** — token จะผ่านก็ต่อเมื่อผ่าน**ทั้งสองชั้น** คือ ลายเซ็น, `exp` และ `iss` ของ JWT ถูกต้อง (ล็อก algorithm ไว้ที่ HS256 ตัวเดียว token แบบ `alg: none` หรือที่สลับ algorithm จึงไม่ผ่าน) **และ**มีแถวใน `auth_sessions` ที่เป็นของ `sub` คนนั้นและยังไม่ถูกเพิกถอน
*   **Logout** (`POST /auth/logout`) — ตั้งค่า `revoked_at` ของ session นั้น การตรวจชั้นที่สองจะไม่ผ่านตั้งแต่วินาทีนั้น การเพิกถอนจึงมีผลทันที session อื่นของผู้ใช้คนเดียวกันไม่ได้รับผลกระทบ
*   **login ไม่เผยว่าอีเมลไหนมีบัญชี** — รหัสผิดกับอีเมลที่ไม่มีในระบบได้ `401 invalid_credentials` ที่ body เหมือนกันทุกไบต์ อีเมลที่ไม่มีก็ยังต้องเทียบกับ hash หลอกที่ cost เท่ากัน เวลาตอบจึงไม่บอกด้วยว่ามีบัญชีหรือไม่
*   **service อื่นตรวจ token ผ่าน `GET /auth/me`** แบบ REST ([ADR-002](./0002-use-restful-api-internal-communication.th.md)) ไม่ต้องถือ secret สำหรับเซ็น token เอง secret จึงอยู่ที่ service เดียว และการเช็คการเพิกถอนก็อยู่ที่ที่เดียวที่รู้เรื่องนี้ ระหว่างที่ยังไม่มี API Gateway การเรียกนี้คือวิธีบังคับข้อ "ปฏิเสธด้วย 401" ของ NFR-005
*   **Secret สำหรับเซ็น token** — ต้องตั้ง `AUTH_JWT_SECRET` และต้องยาวอย่างน้อย 32 ไบต์ (ขนาด key ขั้นต่ำของ HS256 ตาม RFC 7518 §3.2) ตั้งใจไม่ใส่ค่า default ไว้ในโค้ด ถ้าไม่ได้ตั้ง service จะไม่ยอมสตาร์ต ส่วน `docker-compose.yml` มีค่าสำหรับ dev เท่านั้น

**การ hash รหัสผ่าน — ใช้ scrypt ของ Werkzeug เป็นตัวเทียบเท่า bcrypt ตาม NFR-004:**
NFR-004 ยก bcrypt เป็นตัวอย่าง สาระของข้อกำหนดคือต้องใช้ hash ที่ช้า มี salt และออกแบบมาสำหรับรหัสผ่าน แทนการเก็บ plaintext หรือใช้ hash ทั่วไปที่เร็ว เราใช้ `werkzeug.security.generate_password_hash(password, method="scrypt:131072:8:1")` ซึ่งเทียบเท่า bcrypt ในทุกคุณสมบัติที่ NFR-004 ต้องการ และแข็งแรงกว่าในบางด้าน

*   **มี salt ต่อรหัสผ่าน** — Werkzeug สุ่ม salt ใหม่ทุกครั้งที่ hash รหัสผ่านเดียวกันจึงได้ hash ต่างกัน และตารางที่คำนวณไว้ล่วงหน้าใช้ไม่ได้ มีเทสต์ยืนยันข้อนี้
*   **ปรับ cost ได้ และเก็บ cost ไว้ใน hash** — เหมือน `$2b$<cost>$` ของ bcrypt ตัว hash บันทึก `scrypt:<N>:<r>:<p>` ไว้ จึงเพิ่ม cost ทีหลังได้โดย hash เดิมยังใช้ได้
*   **เทียบแบบ constant-time** — `check_password_hash` เทียบด้วย `hmac.compare_digest`
*   **กินหน่วยความจำ (memory-hard)** — ที่ค่านี้ hash หนึ่งครั้งใช้หน่วยความจำประมาณ 128 MiB (bcrypt ใช้ประมาณ 4 KiB) การถอดรหัสด้วย GPU/ASIC จึงแพงขึ้นมาก
*   **OWASP จัดอันดับให้สูงกว่า bcrypt** — [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) เรียงคำแนะนำเป็น Argon2id → scrypt → bcrypt → PBKDF2 กำหนดค่าขั้นต่ำของ scrypt ไว้ที่ N=2^17, r=8, p=1 และให้ bcrypt (work factor ≥ 10) เป็นตัวเลือกสำหรับระบบเก่า
*   **ไม่ตัดรหัสผ่านที่ 72 ไบต์** — bcrypt ไม่สนส่วนที่เกิน 72 ไบต์ ตัวอักษรไทยใช้ 3 ไบต์ต่อตัวใน UTF-8 รหัสผ่านภาษาไทยตั้งแต่ประมาณ 25 ตัวอักษรขึ้นไปจึงจะถูกตัดทิ้งโดยไม่มีใครรู้ scrypt ไม่มีข้อจำกัดนี้ ส่วนเพดาน 128 ตัวอักษรที่ตั้งไว้มีไว้จำกัดขนาด request เท่านั้น
*   **ไม่เพิ่ม dependency** — Werkzeug มากับ Flask อยู่แล้วและใช้ `hashlib.scrypt` ของ OpenSSL ไม่ต้อง build C extension เพิ่มใน image

ค่า default ของ Werkzeug เองคือ N=2^15 ซึ่ง**ต่ำกว่า**ขั้นต่ำของ OWASP จึงต้องระบุค่าเองใน `credentials.py` และมีเทสต์ที่จะ fail ถ้าค่าเปลี่ยน วัดบนโน้ตบุ๊กที่ใช้พัฒนาได้ประมาณ 0.4 วินาทีต่อการ hash หนึ่งครั้ง (2026-09-25)

**ทางเลือกที่พิจารณา:**
*   **JWT แบบ stateless อย่างเดียว ให้ logout แปลว่า "client ลืม token ไปเอง"** — ไม่เลือก เพราะ token ยังใช้ได้จนถึง `exp` ซึ่งไม่ผ่านข้อ "invalidate ทันที" ของ #6
*   **ใช้ session token แบบสุ่ม (opaque) แทน JWT** — ง่ายที่สุดและเพิกถอนได้เหมือนกัน แต่ไม่เลือก เพื่อให้ตรงกับ JWT ที่ C4 diagram และ NFR-005 กำหนด และเพื่อให้ gateway ในอนาคตอย่างน้อยปฏิเสธ token ปลอมหรือหมดอายุได้เองก่อนต้องถาม auth-service
*   **ทำ authentication ไว้ใน `notes-service`** — container น้อยลง แต่ขัดกับ ADR-001 และ NFR-013 และผูก identity ไว้กับ schema ของโน้ต
*   **ใช้ package `bcrypt` หรือ `argon2-cffi`** — ต้องเพิ่ม native dependency ทั้งคู่ Argon2id เป็นตัวเลือกแรกของ OWASP และเพราะ hash แต่ละตัวบันทึก method ของตัวเองไว้ ถ้าจะย้ายไปใช้ทีหลังก็แค่ hash ใหม่ตอนผู้ใช้ login สำเร็จครั้งถัดไป

**ผลที่ตามมา:**
*   **ข้อดี:**
    *   AC ทุกข้อของ #5 และ #6 มีเทสต์อัตโนมัติรองรับ รวมถึง "logout แล้วใช้ไม่ได้ทันที" และ "รหัสผิดกับอีเมลที่ไม่มีได้คำตอบเดียวกัน"
    *   ตอนนี้มี identity ที่เชื่อถือได้ให้ flow อัปโหลดดึงชื่อผู้อัปโหลดไปแนบ (US-31) แทนการอ่านจากฟอร์ม
    *   secret สำหรับเซ็นอยู่ที่ service เดียว และ hash แต่ละตัวพก method กับ cost ของตัวเองไว้ จึงเปลี่ยนหรืออัปเกรดทั้งสองอย่างทีหลังได้
*   **ข้อเสีย:**
    *   **ยังไม่มีการยืนยันอีเมล** การเช็คโดเมนพิสูจน์ได้แค่ว่าอีเมล*หน้าตา*เป็นของมหาวิทยาลัย ไม่ได้พิสูจน์ว่าคนสมัครเป็นเจ้าของอีเมลนั้น ใครก็สมัครด้วยอีเมล `@up.ac.th` ของคนอื่นได้ Email Service ใน C4 diagram อยู่นอกขอบเขต AC ของ #5 แต่ต้องทำก่อน deploy สู่สาธารณะ โดยเฉพาะเพราะ `display_name` (ซึ่งก็คือเครดิตที่แสดงบนโน้ต) ผู้ใช้ตั้งเอง
    *   หน้าสมัครเผยว่าอีเมลไหนมีบัญชีแล้ว (`409`) เพราะ #5 บังคับให้ตรวจอีเมลซ้ำ จึงเลี่ยงไม่ได้ที่หน้าสมัคร แต่หน้า login ยังไม่เผย
    *   ยังไม่จำกัดจำนวนครั้งที่ login การ brute-force ถูกชะลอด้วย cost ของ scrypt อย่างเดียว เป็นงานต่อยอด
    *   การยอมทิ้งความเป็น stateless ทำให้ทุก request ที่ต้องยืนยันตัวตนไปยัง service อื่นมีค่าใช้จ่ายเพิ่ม คือเรียก HTTP ไปที่ auth-service หนึ่งครั้งและค้นฐานข้อมูลหนึ่งครั้ง
    *   ยังไม่มีการรีเซ็ตรหัสผ่าน ไม่มีการแก้โปรไฟล์ และยังไม่มีการล้างแถว `auth_sessions` ที่หมดอายุแล้ว
    *   bearer token ปลอดภัยเท่าที่ช่องทางส่งปลอดภัย การ deploy จริงต้องใช้ HTTPS ระหว่างนี้กฎของ ADR-003 ยังใช้อยู่ คือห้ามเปิด service สู่อินเทอร์เน็ตสาธารณะ
*   **ขอบเขตของการเปลี่ยนแปลงนี้:** เพิ่มเฉพาะ `auth-service` ส่วน `notes-service` ยังไม่ได้เรียกใช้ การอัปโหลดจึงยังรับ `uploader_name` จากฟอร์มอยู่ การบังคับ login ตอนอัปโหลดและดึงชื่อผู้อัปโหลดจากบัญชีเป็นงานรอบถัดไป (refs #31) edit token ของ [ADR-004](./0004-per-note-edit-token.th.md) ยังใช้ต่อ ADR นี้ยังไม่ได้แทนที่ ADR-004 ตารางใหม่เป็นการเพิ่มล้วน การเปลี่ยนแปลงนี้อย่างเดียวจึงยังไม่ต้อง `docker compose down -v`
