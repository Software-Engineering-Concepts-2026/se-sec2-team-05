# ADR-013: เลิกใช้ edit token ต่อโน้ต

[🌐 English](./0013-retire-per-note-edit-token.md) · **ภาษาไทย**

**สถานะ:** Accepted · แทน ADR-004 และจำกัดขอบเขตของ ADR-008

**บริบท:**
ADR-004 ให้โน้ตทุกใบมี edit token แบบสุ่มเป็นตัวแทนการตรวจความเป็นเจ้าของ ในช่วงที่ระบบยังไม่มีการ login และระบุไว้ว่าให้รื้อออกเมื่อมี User & Auth Service · ต่อมา ADR-005 เพิ่ม service นั้น US-31 ให้ผู้อัปโหลดมาจากบัญชีที่ login (`uploader_id`) และ ADR-008 ให้ผู้อัปโหลดที่ login อยู่แก้และลบโน้ตของตัวเองได้ โดยยังเก็บ token ไว้เป็นอีกทาง · หลังจากนั้น token มีแต่ต้นทุน: ผู้ใช้ต้องเก็บรหัสลับเพิ่มอีกอย่าง มีหน้าแก้ไขแยกที่ข้ามการ login การตรวจสิทธิ์ทุกจุดมีสองทาง และ gateway ต้องยกเว้น header นี้เป็นกรณีพิเศษ

**การตัดสินใจ:**
*   การแก้ (`PATCH /notes/<id>`) และลบ (`DELETE /notes/<id>`) โน้ต **ต้อง login เป็นบัญชีที่อัปโหลดโน้ตนั้น** · ไม่ login ได้ `401` บัญชีอื่นได้ `403` เหมือน ADR-008
*   `POST /notes` ไม่คืน `edit_token` อีก และ header `X-Note-Token` ถูกเมิน
*   คอลัมน์ `notes.edit_token_hash` ถูกลบด้วย Alembic revision `0002` (ADR-010) และลบไฟล์ `tokens.py`
*   หน้าเว็บเอา `edit.html` และกล่องรหัสหลังอัปโหลดออก · เจ้าของแก้และลบจากหน้าโปรไฟล์ (ADR-008) ส่วนหน้าโน้ตและหน้าอัปโหลดมีลิงก์ไปที่นั่น
*   การตรวจรายงานของผู้ดูแลเหมือนเดิม: ผู้ดูแลลบโน้ตที่ถูกรายงานผ่าน `/reports/<id>/note` (ADR-007)

**ผลที่ตามมา:**
*   เหลือทางพิสูจน์ความเป็นเจ้าของทางเดียว ซึ่ง auth-service ตรวจและเพิกถอนได้ (logout) · gateway ไม่ต้องมีข้อยกเว้นเรื่อง token
*   token ที่เคยแจกไปใช้ไม่ได้อีก · ผู้อัปโหลดโน้ตเดิมยังแก้/ลบได้ด้วยการ login เพราะโน้ตทุกใบมี `uploader_id` อยู่แล้ว (US-31)
*   การแก้ไขต้องพึ่ง auth-service · ช่วงที่ auth-service ล่ม การแก้/ลบได้ `503` เหมือน route อื่นที่ต้อง login
*   downgrade ของ migration กู้ hash เดิมคืนไม่ได้ ใส่คอลัมน์กลับมาเป็นค่าว่าง
